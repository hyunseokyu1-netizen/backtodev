## Things the Builder's Eyes Can't See

I've been building **MatchDa**, a side project for landing jobs abroad. You enter your career history in
Korean, AI turns it into an English resume, and once you register the careers pages of companies you're
interested in, it automatically collects job postings and scores how well they match you.

The feature set had come together enough that I was about to start promoting it in some communities, when
a thought hit me.

> "I use this service every day. But would it feel natural to someone who just showed up for the first
> time?"

A builder can never truly become a new user. I already know where to click and in what order to use
things. So before promoting it, I walked back through the entire journey — **sign up → enter a resume →
find postings → build application documents** — from the perspective of a brand-new user.

The result? Had I started promoting without catching this, it would have been a disaster: **4 P0-level
problems.** This post is the record of finding and fixing those 4.

## Review Method: Looking at the Code and the Live Site Together

Doing a self UX review by only looking at the browser misses "why does it behave this way," and only
looking at the code misses "what does this actually look like." So I did both in parallel.

1. **Explore the live site like a brand-new user** — landing → signup → onboarding → core feature, in
   that order, checking at every step whether "a first-time visitor would know what to do next"
2. **Immediately check the code for that screen** — whenever I found a problem, I'd open the component
   and server action rendering that screen to understand the cause and scope of the fix

Doing it this way means never stopping at "this feels off" — it goes straight to "fix line X of file Y."

## P0-1. Fake Mockup-Era Statistics Were Still Live on the Landing Page

The scariest find. The landing page had a stats band showing:

- "12,000+ active users"
- "45+ countries with international job postings"
- "81% average job match rate"

**Placeholder numbers from the design mockup phase were live on the real-service landing page,
unchanged.** The hero section even had 4 fake user avatars and social proof copy reading "Join 12,000
Korean professionals already using this."

Why is this P0?

- The instant someone in a community I promote to asks "it says 12,000 people, so why isn't there a
  single review anywhere?" **trust collapses entirely, all at once**
- There's also a real risk under advertising law regarding false or exaggerated claims

### Fix: Replace Numbers With Verifiable Facts

Instead of swapping fake numbers for plausible-looking real numbers, I **dropped the promise of numbers
entirely and replaced it with feature-based copy.**

```ts
// src/lib/matchda/i18n.ts — before
stats: [
  { value: '45개국+', label: '해외 채용 공고' },
  { value: '12,000+', label: '활동 중인 사용자' },
  { value: '81%', label: '평균 직무 매칭률' },
  { value: '3분', label: '평균 이력서 번역 시간' },
],
```

```ts
// after — 전부 지금 당장 사실인 것들
stats: [
  { value: 'AI 번역', label: '한국어 이력서 → 전문가 수준 영어' },
  { value: '4종 ATS', label: 'Greenhouse · Lever 등 채용페이지 자동 인식' },
  { value: '공고별', label: '맞춤 이력서 · 커버레터 자동 생성' },
  { value: '₩0', label: '무료로 시작 · 카드 등록 불필요' },
],
```

I removed the fake avatars and social-proof block from the component entirely. Once real users actually
pile up, those numbers can be brought back for real.

> **Lesson**: if a project started from a design mockup, moving to a real service requires a full audit
> of **just how much mockup data is still alive.** Copy stored as "data," like an i18n dictionary, is
> especially easy to overlook.

## P0-2. What the Search Bar Promised Didn't Match What the Product Delivers

The landing hero had a slick search bar — a "all countries" selector, trending search chips like
"Berlin · Backend" and "Singapore PM." At a glance it looks like **a platform that searches a global
database of job postings.**

But the real product is a tool that shows "postings scraped from the career pages you've registered."
If a new user types "Berlin backend" into that search bar and signs up, what happens? **Zero registered
sources means the search result is guaranteed to be empty.**

This kind of expectation-vs-reality gap leads directly to churn. Users don't think "oh, I guess I need to
register a company first" — they generously assume the worst and think "search is broken, this is no
good."

### Fix: Scale the Promise Down to Match Reality

Ideally, opening the shared job pool to logged-out users too so the search actually works for real would
be the right fix (added to the backlog), but as an emergency measure before promoting, I **scaled the
copy's promise down to match the service's actual scope.**

| Item | Before | After |
|---|---|---|
| Country selector | All countries | Australia · New Zealand |
| Trending search chips | Berlin · Backend, Singapore PM | Sydney · Backend, Melbourne · Full Stack, Auckland · Data |
| Subheading | "Search job postings worldwide" | "Automatically collect postings from companies you care about, and search by role and skill" |

The positioning also narrowed from "45 countries, global" to **"Australia/New Zealand IT."** Starting
small and expanding once it works beats promising broad and failing to deliver.

## P0-3. New Users Were Dropping Into a "Blank Screen"

Walking through the signup/login flow directly, here's what happened.

1. Sign up → verify email → log in
2. Unconditionally redirected to `/discover` (job discovery)
3. But there's no resume (profile) yet, so **every match score is meaningless**
4. The only guidance is a thin banner at the top

This service's "aha moment" is **the moment you type in Korean and an English resume comes out.** That
experience needs to happen within the first 3 minutes of signing up, but instead users were being dropped
onto an empty job-discovery screen and left to find their own way.

### Fix: Branch the Post-Login Destination on the Server

I created a server action that decides the destination based on whether onboarding is complete.

```ts
// src/app/auth-actions.ts
export async function postLoginPath(): Promise<string> {
  const email = await getAuthUserEmail()
  if (!email) return '/login'
  const profile = await getOrCreateProfile(email)
  return profile?.onboarding_completed ? '/discover' : '/onboarding'
}
```

I wired this into two places.

**① On successful email login** (calling the server action from a client component):

```ts
// src/app/login/LoginForm.tsx
const { postLoginPath } = await import('@/app/auth-actions')
router.push(await postLoginPath())
```

**② The OAuth/signup verification callback** — one thing to watch out for here. The callback route also
handles entries that specify a `next` parameter, like password reset flows, so the onboarding branch
should only fire **when `next` is absent.**

```ts
// src/app/auth/callback/route.ts
if (!next) {
  const email = await getAuthUserEmail()
  if (email) {
    const profile = await getOrCreateProfile(email)
    if (profile && !profile.onboarding_completed) target = '/onboarding'
  }
}
```

Any forced flow always needs an exit. I also added a "Skip for now →" link to the onboarding header.

## P0-4. Even Users With a Resume File Had to Type Out 8 Chat Steps

Onboarding is a chat-style flow asking name → contact → education → experience → skills → desired
role... 8 steps. It's not a bad design if you're happy to answer comfortably in Korean, but the problem
is **most people preparing to work abroad already have a resume file.** Making those people retype their
education and work history from scratch is torture.

What made it even more galling: a server action (`analyzeResumeFile`) that parses an uploaded resume
PDF/DOCX with AI and structures it **already existed, on the profile page.** It just wasn't exposed in
onboarding.

### Fix: An Upload Card That Reuses the Existing Action

No need to build anything new — I just added a single upload-card component on top of the onboarding
chat.

```tsx
// src/app/onboarding/ResumeUploadOption.tsx (핵심만)
async function handleFile(e: React.ChangeEvent<HTMLInputElement>) {
  const file = e.target.files?.[0]
  if (!file) return
  setBusy(true)

  const fd = new FormData()
  fd.append('resume', file)
  const res = await analyzeResumeFile(fd) // 기존 서버 액션 재사용

  if (res.error) { setError(res.error); return }

  // 파싱 결과를 확인·수정할 수 있게 이력서 스튜디오로
  router.push('/profile')
}
```

Since `analyzeResumeFile` already handles setting `onboarding_completed: true` internally, one upload is
enough to finish onboarding entirely. 8 chat steps collapsed into a single click.

> **Lesson**: UX problems don't always need new code. Surprisingly often, it's just a case of **a feature
> that already exists not being surfaced where it's actually needed.**

## Verification and the Commit

After making the fixes, I ran a type check, a production build, and checked the actual rendered result on
a local server.

```bash
npx tsc --noEmit          # 타입 체크
npx next build            # 프로덕션 빌드
npx next start -p 3457    # 로컬에서 띄우고
curl -s localhost:3457/ | grep -c "12,000"   # → 0 (가짜 통계 사라짐 확인)
```

For flows that require login (redirect branching, actual file upload), a build check alone wasn't enough,
so I made it a rule to personally walk through sign up → upload once before deploying.

## Wrap-Up — A Pre-Promotion Self UX Review Checklist

Generalizing what I went through: before telling the world about a side project, check at least this
much.

1. **A full audit of mockup data** — do fake stats, testimonials, or avatars from the design phase still
   survive in the real service? (Watch i18n dictionaries and mock-data files especially closely.)
2. **The landing's promise vs. the product's reality** — can a new user actually get, right after
   signing up, the experience the first screen promised them? Are there paths that lead to an empty
   screen?
3. **The path right after signup** — how many clicks does it take for a user to reach the service's "aha
   moment"? Does the system walk them there, or does the user have to go find it themselves?
4. **Where existing features are surfaced** — is a feature that would reduce friction hiding exactly when
   it's needed most?

The builder's eyes are already contaminated. Before hitting the promote button, take one day and
**become your own service's new user.** That one day is what let me clear out 4 problems that could have
wrecked trust, before any guests showed up.
